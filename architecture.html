Selected certificate model and considered alternatives

A certificate enables encrypted, authenticated HTTPS; it does not make an application public. Routing and firewall policy still keep every application private.

DNS-01 public certificate flow

DNS-01 proves control of the public domain with a temporary TXT record. Cloudflare hosts the authoritative zone and its API creates the challenge record; private application addresses remain only in AdGuard.

How zones are implemented

Firewall routerCreates each VLAN gateway, routes between zones, supplies DHCP, applies default-deny ACLs, performs WAN NAT, and holds the WireGuard-subnet return route.

ProxmoxMakes vmbr0 VLAN-aware, places host management on VLAN 10, and assigns one VLAN tag to each VM NIC.
Guest VMReceives a normal untagged VirtIO NIC, IP address, and VLAN gateway; no VLAN configuration is required inside a single-zone guest.

Wireless APMaps trusted and IoT SSIDs to their VLANs. Wireless management remains on VLAN 10.

Applications

WireGuard + AdGuard + Cloudflare DDNS

WireGuard is the sole remote ingress. AdGuard provides DNS to VPN clients and selected local devices. A systemd timer reconciles the DNS-only vpn.<domain> A record with the current public IPv4 every five minutes.

No application is exposed directly to the public internet.

Durable: VPN identities, peer assignments, DNS rules, and credentials. The updater itself has no durable application state. Deployment: native WireGuard, an Ansible-managed AdGuard Compose project, and an Ansible-managed unprivileged DDNS service.

/etc/homelab/ddns/cloudflare.env, owned by root:cloudflare-ddns with mode 0640; excluded from Git and Terraform

Outbound HTTPS only; the updater introduces no new inbound port

Shared services boundary

Gitea, planned n8n, and future Nextcloud share one VM-level trust, maintenance, and failure boundary to reduce host memory use. Vaultwarden remains allocated a dataset but its deployment is deferred. Each deployed application has a separate Compose project, container network, secret set, and ZFS-backed dataset.

Deliberate limits

  • SQLite is suitable for the initial low-concurrency workload but is the scaling limit; migration to PostgreSQL requires a planned conversion and restore test.
  • TLS, an internal reverse proxy, SMTP, off-host backups, restore automation, upgrades, and removal workflows are not implemented.
  • CI jobs never execute on this VM or on lab-agents-01. Planned lab-runner-01 receives no application datasets or deployment credentials. Runner isolation remains an explicit security boundary.

Workflow change path

  1. Exported workflow definitions live in a private Gitea repository without credential values.
  2. Hermes may propose JSON or supporting-code changes on a feature branch using its restricted Gitea identity.
  3. A human reviews the diff and tests the workflow before importing or promoting it into n8n.
  4. n8n publishes the reviewed version; Hermes receives execution-only access to the specific workflow tool.

Git provider: n8n's licensed native source-control feature accepts ordinary SSH or HTTPS Git repositories, so Gitea is the intended provider. If Community Edition is used, Task will instead own explicit workflow JSON export/import around the same Gitea review flow. The native feature is not assumed until the n8n edition is chosen.

Security boundary

  • Internal TLS is required before transmitting an MCP, webhook, API, or Git credential.
  • Do not give Hermes the instance-level n8n MCP administration surface; it can create and edit workflows in addition to running them.
  • Each exposed workflow has a strict input schema, timeout, bounded output, dedicated least-privilege credential, and no arbitrary command or URL parameter.
  • Read-only or reversible workflows come first. Destructive or externally visible actions require a separate human-approval design.
  • The n8n encryption key is a separately handled secret and must be recoverable with the durable dataset; neither belongs in Git or Terraform.

Open choices

  • Open Select Community, Business, or Enterprise edition and therefore the Gitea synchronization mechanism.
  • Open Confirm SQLite for the single-process pilot or PostgreSQL if expected concurrency or operational requirements justify it.
  • Open Define the first workflows and classify each as read-only, reversible write, approval-required, or prohibited.

Shared deployment contract

  1. Packer builds the generic Ubuntu image.
  2. Terraform creates each VM, OS disk, network attachment, and data attachment.
  3. Ansible installs and configures applications.
  4. Application data is restored or mounted from ZFS-backed storage.
  5. Hermes proposes code and n8n workflow definitions through branches; CI tests what can be automated; a human approves merges, workflow publication, and deployment.

Terraform owns only each VirtioFS mapping and VM attachment. ZFS datasets live outside Terraform state, so ordinary VM destruction cannot delete durable data.
