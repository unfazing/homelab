Agent management boundary: Ansible-owned nftables rules on lab-agents-01 block agent-initiated guest and container IPv4 connections to Proxmox .10, router management .254 (DNS remains allowed), and legacy .9 except Inkling TCP 3000. Current AdGuard HTTPS path

Private name
adguard.home.<domain> resolves to Caddy at 192.168.1.101 only through the new AdGuard DNS server at 192.168.1.100. The old .9 resolver does not serve this name; router and VPN DNS have not been cut over.
Client connection
A home LAN client reaches Caddy on TCP 443. Remote access requires a WireGuard tunnel with a route to 192.168.1.101; that route has not yet been verified during migration. Caddy presents the production wildcard certificate and forwards the request to AdGuard; there is no WAN forward for TCP 443.
Backend connection
Caddy sends HTTP to 192.168.1.100:3000 across the current flat LAN. The access VM admits this backend port only from Caddy and itself, so ordinary clients use HTTPS rather than the direct HTTP port. This source-IP rule is not encryption or strong isolation against a compromised LAN host.
Client policy
No client certificate or client-IP allowlist is configured at Caddy. Any client with private network reachability to Caddy can reach the login page; AdGuard's own password is required to administer it. Whether to add client restrictions after VLAN migration remains open.

Selected certificate model and considered alternatives

A certificate enables encrypted, authenticated HTTPS; it does not make an application public. Routing and firewall policy still keep every application private.

Applications

WireGuard + AdGuard + Cloudflare DDNS

WireGuard is the sole remote ingress. The old AdGuard and WireGuard services remain active at 192.168.1.9 during migration. The parallel resolver at 192.168.1.100 uses a reviewed DNS policy: adguard.home.net points to the new DNS address, while the HTTPS administration name adguard.home.<domain> and Gitea resolve privately to Caddy at 192.168.1.101. Router and VPN client DNS still point to the old service. A systemd timer on the new access VM already reconciles the DNS-only vpn.<domain> A record with the current public IPv4 every five minutes.

No application is exposed directly to the public internet.

Durable: VPN identities, peer assignments, AdGuard configuration, and query data. The updater itself has no durable application state. Deployment: native WireGuard, a digest-pinned Ansible-managed AdGuard Compose project, and an Ansible-managed unprivileged DDNS service.

AdGuard DNS and UI
Host networking preserves DNS client addresses; plain DNS binds only to 192.168.1.100:53. Caddy terminates HTTPS for adguard.home.<domain> on the services VM and proxies to 192.168.1.100:3000. A dedicated nftables rule admits that HTTP backend only from Caddy's address and guest-local traffic; Docker requires the firewall unit on boot. No client certificate or IP allowlist is configured at Caddy. Explicit container config and work paths point to the ZFS-backed mount.
AdGuard policy
Two DNS-over-HTTPS upstreams in load-balancing mode, four bootstrap resolvers, five subscribed filters (three active), the AdGuard and router rewrites plus private Gitea and Hermes, and the existing 90-day query-log retention on unencrypted ZFS. Broader rewrite planning is deferred. Initial setup and idempotent reconciliation use the local API; the running YAML is not edited directly. Source-controlled policy supersedes dashboard edits on the next deployment. Existing OISD Big and Small overlap and can be rationalized only after parity testing.
AdGuard secret
A new administrator password is generated outside Git, copied to a root-only file on the VM, and not stored on the persistent dataset.
Secret boundary
/etc/homelab/ddns/cloudflare.env, owned by root:cloudflare-ddns with mode 0640; excluded from Git and Terraform
Failure behavior
No update occurs unless the token sees exactly one active zone and DNS contains no more than one matching A record
Network effect
Outbound HTTPS only; the updater introduces no new inbound port

Shared services boundary

Gitea, planned n8n, and future Nextcloud share one VM-level trust, maintenance, and failure boundary to reduce host memory use. Vaultwarden remains allocated a dataset but its deployment is deferred. Each deployed application has a separate Compose project, container network, secret set, and ZFS-backed dataset.

Deliberate limits

  • SQLite is suitable for the initial low-concurrency workload but is the scaling limit; migration to PostgreSQL requires a planned conversion and restore test.
  • TLS, an internal reverse proxy, SMTP, off-host backups, restore automation, upgrades, and removal workflows are not implemented.
  • CI jobs never execute on this VM or on lab-agents-01. Planned lab-runner-01 receives no application datasets or deployment credentials. Runner isolation remains an explicit security boundary.

Workflow change path

  1. Exported workflow definitions live in a private Gitea repository without credential values.
  2. Hermes may propose JSON or supporting-code changes on a feature branch using its restricted Gitea identity.
  3. A human reviews the diff and tests the workflow before importing or promoting it into n8n.
  4. n8n publishes the reviewed version; Hermes receives execution-only access to the specific workflow tool.

Git provider: n8n's licensed native source-control feature accepts ordinary SSH or HTTPS Git repositories, so Gitea is the intended provider. If Community Edition is used, Task will instead own explicit workflow JSON export/import around the same Gitea review flow. The native feature is not assumed until the n8n edition is chosen.

Security boundary

  • Internal TLS is required before transmitting an MCP, webhook, API, or Git credential.
  • Do not give Hermes the instance-level n8n MCP administration surface; it can create and edit workflows in addition to running them.
  • Each exposed workflow has a strict input schema, timeout, bounded output, dedicated least-privilege credential, and no arbitrary command or URL parameter.
  • Read-only or reversible workflows come first. Destructive or externally visible actions require a separate human-approval design.
  • The n8n encryption key is a separately handled secret and must be recoverable with the durable dataset; neither belongs in Git or Terraform.

Open choices

  • Open Select Community, Business, or Enterprise edition and therefore the Gitea synchronization mechanism.
  • Open Confirm SQLite for the single-process pilot or PostgreSQL if expected concurrency or operational requirements justify it.
  • Open Define the first workflows and classify each as read-only, reversible write, approval-required, or prohibited.

Shared deployment contract

  1. Packer builds the generic Ubuntu image.
  2. Terraform creates each VM, OS disk, network attachment, and data attachment.
  3. Ansible installs and configures applications.
  4. Application data is restored or mounted from ZFS-backed storage.
  5. Hermes proposes code and n8n workflow definitions through branches; CI tests what can be automated; a human approves merges, workflow publication, and deployment.

Terraform owns only each VirtioFS mapping and VM attachment. ZFS datasets live outside Terraform state, so ordinary VM destruction cannot delete durable data.
