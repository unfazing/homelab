Command flow

  1. task doctor validates tools, credentials, connectivity, and source files without changing infrastructure.
  2. Explicit network and Proxmox-host tasks establish prerequisites; they are never hidden inside normal deployment.
  3. Packer creates the generic template.
  4. Terraform creates the VM topology and emits machine-readable outputs.
  5. An inventory script writes .generated/ansible/hosts.json atomically from those outputs.
  6. Ansible converges applications, then verification tasks test health and network policy.
  7. Backup and data-destruction tasks remain separate from compute deployment and destruction.

Boot networking contract

  1. The kernel and initramfs mount the local LVM-thin root disk without bringing up a network.
  2. Cloud-init reads the per-VM Proxmox seed, applies the hostname, SSH key, and network definition, then the installed Ubuntu systemd-networkd service configures the NIC.
  3. Terraform must attach a cloud-init drive and supply a valid ipconfig0; there is deliberately no installer-network fallback.
  • The Dracut omission file persists, so future kernel upgrades regenerate initramfs without dyn-netconf or initramfs systemd-networkd.
  • DHCP, static addressing, and VLAN-tagged NICs remain supported after root mounts. Network availability may occur a few seconds later, and Terraform waits for the guest agent.
  • The current F620 DHCP service is not suitable for concurrent clone validation; prefer excluded static test addresses until the target firewall router owns DHCP.
  • A VM whose root disk is hosted over NFS, iSCSI, or another network-root technology requires a separate image with initramfs networking enabled.

Acceptance criteria

  • Packer formatting and validation pass before the build begins.
  • The build uses a pinned Ubuntu release and verified checksum.
  • The template resides on NVMe/LVM-thin and its disk is no larger than the smallest planned VM root disk.
  • A clone obtains its intended cloud-init identity, address, and administrator SSH key.
  • The clone has non-empty machine and SSH host-key identities; cross-clone uniqueness is explicitly reported as not run.
  • The temporary packer account, installer network configuration, logs, and credentials are absent.
  • QEMU guest agent reports successfully to Proxmox.
  • No application, durable data, or application secret is embedded in the template.

Verification safety

  • Guarded Refuse to run unless VM ID 9900 is free and VM 9000 is a template.
  • Isolated Keep verification state and credentials under ignored .generated/; destroy only resources in that state.
  • Recoverable Retain Terraform state and report cleanup failure instead of losing ownership of test VMs.
  • Diagnostic Name each guest assertion, distinguish fatal cloud-init errors from recoverable warnings, emit status and journal context on failure, and query the guest agent briefly when Terraform has not yet observed an address.
  • Observed Manual clones 200 and 201 initially had no ipconfig0; their Proxmox seeds contained DNS only. Adding ipconfig0=ip=dhcp gave clone 200 IPv4 and IPv6 link-local connectivity, proving the local-root Dracut design.
  • Router blocker Clone 201 had a distinct MAC, SMBIOS UUID, machine ID, and DHCP identity, but the F620 sent its Offer to clone 200's Ethernet MAC. Neither dhcp-identifier: mac nor DHCP's broadcast flag corrected the malformed frame. Select excluded static test addresses or wait for the firewall-router DHCP cutover.
  • Single clone On 2026-09-14, task image:verify created VM 9900, obtained 192.168.1.15, passed all functional assertions with two recoverable cloud-init warnings, wrote the non-secret report, and destroyed the VM.
  • Fail closed Treat either a non-zero Dracut exit, a logged Dracut error, or a generated initramfs that still contains dracut-default.network as a build failure.
  • Deferred Restore the two-clone identity and independent-address assertions after the current F620 DHCP dependency is removed.

  4. The persistent-data role verifies the homelab-gitea VirtioFS mount before the application role assigns UID/GID 1000.

  7. Only after the health endpoint passes does Ansible create homelab-admin. Ansible streams the password over standard input to the Gitea CLI; the secret is not placed in command arguments or written to the VM filesystem.

Implementation sequence

  1. Domain Use home.<domain> as the private application suffix.
  2. DNS verification Cloudflare is active and the VPN record resolves publicly. Review the remaining migrated zone, including verification and CAA records, and confirm no unexpected public application, mail, or website record exists.
  3. Cloudflare activation The API reports one active zone, DNSSEC is active, and the delegated public resolver answers the DDNS record.
  4. Credentials created Separate zone-scoped Cloudflare tokens exist for ACME and DDNS. The DDNS token is installed as a protected host file; install the ACME token only with the future reverse proxy.
  5. DDNS Ansible deployed the Cloudflare updater on lab-access-01; its five-minute systemd timer keeps the DNS-only WireGuard A record aligned with the dynamic public IPv4.
  6. Proxy selection Use Caddy with a reproducibly built Cloudflare module, declarative routes, persistent certificate state, and no Docker-socket mount.
  7. Data The dataset exists and a non-refreshing plan shows one mapping create, one in-place VM 1001 update, and zero destroys. Restore Terraform credentials, run the live plan and apply, then regenerate inventory.
  8. Deploy automation Task and Ansible check, staging, and production paths build the pinned image, verify the Cloudflare module, protect the token, converge Compose, and test the HTTPS health route.
  9. Issue Obtain the wildcard against the ACME staging endpoint, prove automatic renewal, then switch to production while router TCP 80/443 remain closed.
  10. Migrate Place Gitea behind HTTPS, update its advertised URLs, then validate Git, API, clone, and callback behavior before enabling any reusable token.
  11. Extend Route n8n through the same proxy only after the Gitea migration and renewal test pass.

Acceptance criteria

  • Cloudflare is authoritative for the registered domain; all pre-existing public DNS behavior remains intact after migration.
  • The DNS-only WireGuard record follows the dynamic public IPv4 through the Cloudflare updater.
  • A fresh LAN or WireGuard client resolves application names through AdGuard and validates HTTPS without warnings.
  • A LAN-only agent reaches Gitea and approved n8n endpoints over HTTPS without contacting the public CA.
  • The chosen certificate lifecycle introduces no public ingress beyond WireGuard; HTTP-01 and home-hosted authoritative DNS remain disabled.
  • The wildcard private key is readable only by the reverse proxy and is absent from application containers, Git, Terraform state, process arguments, and logs.
  • The Cloudflare zone has no public application A/AAAA records; ACME exposes only temporary TXT challenge data.
  • Automated renewal succeeds in staging and exposes an actionable failure signal before production issuance.
  • Recreating the services VM preserves ACME state through ZFS and Ansible restores the separately managed Cloudflare token.

Implementation sequence

  1. Edition Select the n8n edition and record whether native source control or Task-owned JSON promotion applies.
  2. Database Confirm SQLite for a single-process pilot or PostgreSQL if expected concurrency and recovery requirements justify it.
  3. TLS Implement the internal HTTPS endpoint and client trust before installing any reusable automation credential.
  4. Data Create tank/homelab/services/n8n, add the homelab-n8n mapping, attach it to VM 1001, and verify persistence without replacing the VM.
  5. Deploy Add a dedicated Ansible role and Task check/deploy interface using a reviewed, digest-pinned n8n image and a separately generated encryption key.
  6. Repository Create the private Gitea workflow repository, protect its default branch, and implement the edition-appropriate one-way promotion path.
  7. Identity Give Hermes branch-only repository access and a separate execution credential that cannot administer n8n or enumerate unrelated credentials.
  8. Workflows Select the first workflows and classify each as read-only, reversible write, approval-required, or prohibited.
  9. Expose Publish only approved per-workflow MCP or HTTP tools with strict schemas, timeouts, bounded output, and narrowly scoped downstream credentials.

Acceptance criteria

  • The editor, API, and execution endpoints have no public ingress and use trusted internal TLS.
  • Hermes can execute only explicitly approved workflow tools and cannot list credentials, edit active workflows, or publish a version.
  • Hermes-proposed changes reach only a feature branch; protected-branch merge and n8n promotion require human action.
  • Workflow definitions are recoverable from Gitea while credential values and the encryption key are absent from Git, Terraform state, command arguments, and logs.
  • n8n state survives container and VM recreation through the dedicated ZFS dataset, and ordinary compute destruction cannot delete it.
  • The services VM remains within its memory budget under representative Gitea and n8n activity; otherwise the automation workload is moved to a dedicated VM.
  • A second Ansible convergence reports no changes.
